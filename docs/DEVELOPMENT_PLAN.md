# gPhotos — Development Plan

**Date:** 2026-09-13
**Based on:** [`CURRENT_STATUS_AND_GAPS.md`](CURRENT_STATUS_AND_GAPS.md) and the decisions recorded below.
**Purpose:** A phased, file-level plan to close the identified gaps and move toward a "full proof" (robust, production-ready) gPhotos app. Each phase should ship as one or more reviewable branches; later phases assume earlier ones are merged.

---

## 0. Decisions made (locking these in so we don't re-litigate mid-build)

| # | Topic | Decision |
|---|---|---|
| 1 | Mobile/LAN server auth | PIN/passphrase pairing — set in Settings, mobile browser prompts once, device remembered via session token |
| 2 | AI chatbot | Keep bring-your-own-key for Gemini/OpenAI; invest in making the **offline** local NLP search genuinely strong (no bundled/managed key) |
| 3 | Data layer | Migrate from flat JSON (`library.json` + catalog chunks) to **SQLite** as the source of truth |
| 4 | Location override | Let the existing search-and-assign (Nominatim) flow work on **any** photo, not just unlocated ones |
| 5 | Crop | Build a real crop UI in the Lightbox Edit mode, wired to the existing (currently dead) `cropBox` plumbing |
| 6 | Throttle settings | Wire `delayBetweenPhotosSec` into the **background daemon's** automatic sync loop (not just manual sync); implement real `bandwidthLimitMbps` byte-rate throttling |
| 7 | HEIC rotation bug | Fix immediately — physical mirror-thumbnail file isn't rotated, only metadata/derived caches are |
| 8 | Testing/CI | Migrate to **Vitest**, wire all existing test scripts in, add GitHub Actions CI |
| 9 | Scan/face buttons | Unify into a single scan pass (thumbnail + face detection together) per storage |
| 10 | Cloud drives (OneDrive/Google Drive) | Keep as-is — local-sync-folder only, no direct cloud API integration for now |
| 11 | IPC path hardening | Add a shared path-confinement helper; use it across all main-process IPC handlers and the embedded web server |
| 12 | Sequencing | **Phase 1** bug/security fixes → **Phase 2** infrastructure (testing + SQLite) → **Phase 3** remaining features |

## Phase 1 — Fix now (bugs + security, ship fast)

Goal: stop the bleeding on the two items with real, demonstrated risk — a confirmed data-integrity bug and an unauthenticated network service — before building anything else on top.

### 1.1 Fix HEIC mirror-thumbnail rotation bug
- **Root cause:** `rotatePhotoWithOfflineQueue()` (`src/main/services/virtualMirrorService.ts`) routes any `.heic`-named file into the raw-HEIC rotation branch unconditionally, even when the on-disk bytes are actually a JPEG (as produced by the virtual-mirror thumbnail pipeline). That branch only rotates derived cache copies via `rotateCachedHeicThumbnail()` (`thumbnailCacheService.ts`), never the physical mirror thumbnail file itself.
- **Fix:** reuse the existing magic-byte sniffing already implemented in `rotatePhotoFile()` (checks `0xFF 0xD8` JPEG / `RIFF` WebP headers) at the top of `rotatePhotoWithOfflineQueue()`, so JPEG-bytes-named-`.heic` mirror files are physically rotated in place (same as any other JPEG), while genuinely raw HEIC files keep going through the cache-rotation + rotation-store path.
- **Verify:** `test/test_selected_dedup_and_heic_rotate.ts` Tests 14–15 must pass (currently failing: expects 200×400, gets 400×200). Run the full file — all 28 assertions should pass.
- **Also:** add this test file to `package.json`'s `test` script now (don't wait for the Phase 2 Vitest migration) so this specific regression class can never silently return.

### 1.2 Secure the mobile/LAN web server with PIN pairing
- **New setting:** a PIN/passphrase, generated by default or set by the user in Settings → Mobile Access, stored (hashed, not plaintext) in `library.json`/settings store.
- **Server-side (`embeddedWebServer.ts`):**
  - Add a `/api/auth/pair` endpoint: accepts the PIN, returns a signed session token (e.g. random 32-byte token, stored server-side with an expiry/device label).
  - Every other `/api/*` route checks for a valid `Authorization: Bearer <token>` (or a cookie) and returns 401 if missing/invalid. Exempt only the pairing endpoint and static asset serving needed to render the pairing screen itself.
  - Keep `Access-Control-Allow-Origin: *` only if needed for LAN access patterns; otherwise tighten once the pairing flow is in place.
- **Renderer-side:** when the app is loaded via the embedded server (not Electron) and no valid token is stored (`localStorage`), show a "Enter PIN to continue" screen before rendering the gallery.
- **Desktop settings UI:** Settings → Mobile Access gets a PIN field (set/regenerate), a list of currently-paired devices (label + last-seen) with a revoke button, and the existing LAN URL/QR display.
- **Verify:** extend `test/test_mobile_web_server.ts` to assert unauthenticated requests to write/delete endpoints (`/api/delete-files`, `/api/switch-library`, `/api/library` POST) return 401, and that a valid paired token succeeds.

**Phase 1 exit criteria:** HEIC rotation test suite fully green; mobile web server rejects unauthenticated requests; both changes covered by tests; committed as (at least) two separate, reviewable commits.

## Phase 2 — Infrastructure (testing + data layer)

Goal: get a real safety net and a real database in place before further feature work, since Phase 3 features (especially location override and throttling) will be easier and safer to build correctly on top of this.

### 2.1 Testing: migrate to Vitest, wire everything, add CI
- Add `vitest` (fits the existing Vite build), plus `@vitest/ui` optionally for local debugging.
- Triage the ~34 currently-orphaned test files in `test/`:
  - Pure-logic ones (`verify_core_logic.ts`, `test_500k_catalog_and_sprites.ts`'s benchmark assertions, clustering/dedup math) → convert to real Vitest unit tests with `describe`/`it`/`expect`.
  - Integration ones that spin up real services (`test_heic_pipeline.ts`, `test_checkpoint_and_resume.ts`, `test_thumbnail_worker_throttling.ts`, the new `test_selected_dedup_and_heic_rotate.ts`) → keep as Vitest integration tests using real temp-dir fixtures (they already do this well; mostly a matter of wrapping in Vitest's structure).
  - Ones hardcoded to a developer machine (`test_people_persistence_and_healing.ts`'s reliance on a real `%APPDATA%` library, `test_splash_and_ready.ts`'s hardcoded LAN IP) → rewrite to use isolated temp fixtures instead, or explicitly mark/skip as manual-only if they can't be made portable.
  - Electron-process-spawning ones (`smoke_test_app_ready.js`) → keep as a separate CI job/step, not a Vitest unit test.
- Replace the current `package.json` `test` script with `vitest run` (plus a separate `test:e2e`/`test:smoke` script for the Electron-spawning ones), and make `npm run build` depend on the full suite passing.
- **CI:** add `.github/workflows/ci.yml` — on push/PR: `npm ci`, `npm run build` (which runs tests + typecheck + vite build + electron build), on `windows-latest` (since the app is Windows-first). Add a badge to `README.md`.

### 2.2 Migrate storage layer to SQLite
This is the largest single piece of work in the plan — do it carefully, behind a migration path that never loses user data (faces, names, albums are precious per the user's own explicit requirement).

- **Library choice:** `better-sqlite3` (synchronous, fast, well-supported in Electron via native module rebuild — `electron-builder` already handles native deps for `sharp`, so the precedent exists).
- **Schema (first pass):**
  - `photos` (id, file_path, file_name, file_size, file_date, date_taken, year, month, day, width, height, storage_name, is_favorite, is_excluded, rotation, is_heic_rotated, heic_rotation, sharpness_score, ...) — indexed on `date_taken`, `storage_name`, `(year, month)`.
  - `exif` (photo_id FK, camera_make, camera_model, iso, f_number, exposure_time, focal_length, ...)
  - `locations` (photo_id FK, latitude, longitude, altitude, city, state, country, label) — indexed on `(latitude, longitude)` for map queries.
  - `people` (id, name, cover_face_id, cover_photo_id, created_at)
  - `faces` (id, photo_id FK, person_id FK nullable, box_x/y/w/h, descriptor BLOB, confidence, is_confirmed, is_manual, age, gender, expressions JSON) — indexed on `person_id`.
  - `albums` (id, title, description, cover_photo_id, created_at, updated_at, event_date) + `album_photos` join table.
  - `virtual_storages` (id, name, network_source_path, local_mirror_root, delay_between_photos_sec, bandwidth_limit_mbps, last_synced, ...)
  - `settings` (key, value JSON) — for background-daemon settings, web-server PIN, AI config, etc.
- **Migration:**
  - A one-time migration routine runs on first launch after upgrade: reads the existing `library.json` (and catalog chunks if present), writes everything into the new SQLite DB, and renames `library.json` → `library.json.bak-migrated` (never deletes user data outright).
  - The people-name-preservation guard already in `main.ts`'s `storage:save` needs an equivalent invariant in the new layer: any write that would replace a person's name with a generic `Person N` when a real name is already on record must be rejected/merged, not overwritten. Port `libraryStore.ts`'s `globalPeopleRegistry` restoration logic into a DB-level constraint or an explicit merge function used by every write path.
- **API layer changes:**
  - `catalogService.ts`'s role shrinks to "compute derived summaries" (`timelineSummary`, `placesSummary`, `peopleSummary`) via SQL queries instead of JSON chunk files — `getCatalogPage` becomes a paginated `SELECT ... ORDER BY date_taken DESC LIMIT ? OFFSET ?` (or keyset pagination for better performance at scale).
  - `main.ts`'s `storage:save`/`storage:load` IPC handlers are replaced with more granular handlers matching actual mutations (`photo:update-favorite`, `person:rename`, `album:add-photo`, etc.) instead of one coarse "save the whole blob" — this directly fixes the full-file-rewrite-on-every-save problem and removes the need for the fragile save-queue heuristics.
  - `embeddedWebServer.ts`'s endpoints get the same granular treatment.
  - `zipBackupService.ts` needs to export the SQLite DB (or a JSON dump of it) into the backup zip instead of `library.json`.
- **Testing:** this phase needs strong coverage given the stakes (face/people data must never be lost) — unit tests for the migration routine against representative `library.json` fixtures (including edge cases: photos with no faces, people with custom names, empty albums), and a round-trip test (migrate → read back → assert nothing was dropped or renamed).

**Phase 2 exit criteria:** `npm test` runs a real Vitest suite covering the previously-orphaned tests, CI is green on GitHub Actions, and the app runs entirely on SQLite with a verified, non-destructive migration path from existing `library.json` installs. This is the highest-risk phase — plan for a feature-flagged rollout (e.g. keep the JSON path as a fallback for one release) if you want extra safety margin.

## Phase 3 — Remaining features

These build on Phase 1/2 and can mostly be worked in parallel/any order once the DB migration lands, since none of them depend on each other.

### 3.1 IPC path confinement
- Add `src/main/services/pathSecurity.ts` (or similar) exporting `assertPathInsideAllowedRoots(candidatePath, context)`, checking the resolved absolute path is under one of: the current library root, any configured virtual-storage `localMirrorRoot`/`networkSourcePath`, or the app's own cache/userData directories.
- Apply it at the top of every IPC handler and embedded-web-server route that takes a file path from the renderer/HTTP request: `file:read-base64`, `file:trash-files`, `file:delete-permanently`, `photo:rotate`, `scanner:*`, `storage:read-directory-tree`, the `gphoto://` protocol handler, `/api/photo`, `/api/delete-files`, `/api/switch-library`, `/api/scan`, `/api/file-exists`.
- Decide the failure UX (reject silently vs. surface an error toast) and add tests asserting a `..`-traversal or out-of-root path is rejected on each hardened handler.

### 3.2 Background-daemon throttling (delay + bandwidth)
- Move `delayBetweenPhotosSec` application into `backgroundDaemon.ts`'s `runBackgroundSyncCycle()` loop (currently hardcoded to an 8ms yield), reading it from the relevant `VirtualStorageConfig` already in scope there.
- Implement real `bandwidthLimitMbps` throttling: track bytes written per file copy/thumbnail-generation operation, and after each chunk/file, compute a sleep proportional to `bytesWritten / (bandwidthLimitMbps * 125000)` — same "measure → compute proportional sleep → enforce" pattern already proven in `thumbnailWorkerService.ts`'s CPU throttle.
- Apply consistently to both the manual "Sync Now" path (`virtualMirrorService.syncVirtualStorage`) and the automatic background cycle, so the setting means the same thing in both places.

### 3.3 Location override for already-geotagged photos
- In `PlacesMapView.tsx`, remove the "only show unlocated photos" precondition on the existing Nominatim search-and-assign flow (`handleSearchPlaces`/`handleApplyAssignedLocation`) so it can retarget any selected photo(s)' coordinates, not just unlocated ones.
- Same for the equivalent entry point in `PhotoLightbox.tsx` if one is added there — currently that file only supports label renames, not coordinate changes; decide whether to also surface the full search-and-assign flow from the lightbox or keep coordinate changes map-only.
- Add a confirmation step ("this photo already has a location — replace it?") since this is a destructive-ish edit to existing metadata.

### 3.4 Crop UI
- Add a crop tool to `PhotoLightbox.tsx`'s Edit mode alongside the existing rotate/flip controls: a draggable/resizable rectangle overlay on the canvas preview, producing a `cropBox` in image-pixel coordinates.
- Wire it through the existing `EditPhotoOptions.cropBox` field into `editPhotoFile()` — note the current implementation only exercises `cropBox` via the `nativeImage` fallback branch (when `base64Data` is absent); decide whether to keep that path or instead bake the crop into the canvas-rendered `base64Data` alongside rotate/flip (more consistent with how rotate/flip already work, recommended for consistency).

### 3.5 Unify scan + face-detection into one pass
- Merge the "scan photos" and "scan faces" triggers (in `VirtualStorageView.tsx`/`App.tsx` and the corresponding backend orchestration) into a single per-storage action that runs thumbnail/EXIF scanning and enqueues face detection as part of the same triggered pass, rather than two separate user-initiated steps.
- Preserve the existing per-storage progress UI (thumbnail count + face count) already built — this becomes two progress phases of one job instead of two independent jobs.

## Suggested commit/branch shape

Given the phased structure above, each numbered sub-item (1.1, 1.2, 2.1, 2.2, 3.1–3.5) is sized to be its own branch/PR — small enough to review, large enough to be independently meaningful. Recommended order within Phase 3 (since they're otherwise parallel): 3.2 and 3.5 first (touch the same background-daemon/scan-orchestration code, doing them together avoids rebase pain), then 3.1 (security hardening, self-contained), then 3.3 and 3.4 (independent UI features).

## Open items intentionally deferred (not in scope for this plan)

- Real OneDrive/Google Drive API integration (cloud-only file browsing without local sync) — kept as local-sync-folder-only per decision #10.
- Automatic thumbnail-cache eviction (LRU/size cap) — noted as a gap but not requested for this round; revisit if disk usage becomes a real complaint.
- macOS/Linux desktop support — out of scope; the app remains Windows-first for the desktop client (mobile web already covers other devices via the browser).
